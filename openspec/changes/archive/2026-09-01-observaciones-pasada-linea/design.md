# Design: Observacion Field on Pasada and LineaProduccion

## Technical Approach

Purely additive, single-layer-per-file change: two nullable `text` columns, two entity properties, three Zod schema edits, one optional trailing service parameter, one field-level exception in `PasadaService.update()`, two DTO lines, one Excel column. No new module, no abstraction, no lifecycle rule change. Implements `specs/observaciones-operativas/spec.md` plus the `api-core` / `persistence-core` deltas.

All four proposal assumptions are confirmed decisions: empty string rejected via `min(1)`, `null` clears; no length cap, no audit; `observacion` settable on `LineaProduccion` create; no new authorization rule.

## Architecture Decisions

| # | Decision | Choice | Rejected alternative | Rationale |
|---|----------|--------|----------------------|-----------|
| D1 | `iniciarPasada` signature | 4th trailing optional positional param | Options object | Keeps the ~6 positional call sites in `pasada.service.test.ts` valid untouched; two-field additive change, not a signature redesign. |
| D2 | Closed-state exception | Key-allowlist diff of the payload in `PasadaService.update()` | Separate `updateObservacion()` method; controller-level branch | Keeps one enforcement point; a dedicated method would need a new route + schema and would bypass the generic PUT the spec describes. |
| D3 | Property TS type | `observacion?: string \| null` | `observacion?: string` (mirrors `observacionCierre`) | `null` clearing is a spec requirement; `\| null` makes it type-honest. Precedent exists: `LineaProduccion.rutaAsignadaAt: Date \| null`. |
| D4 | Migration count | One migration file, two `alter table` statements | Two files | `Migration20260710000000_DevicePairing` precedent; one atomic unit, one `down()`. |
| D5 | Excel column key | `observacionInicio` | reuse/rename `obs` | `obs` is bound to `observacionCierre`; a duplicate key silently collides in `addRow`. |
| D6 | Zod on iniciar | `.min(1).optional()` (no `.nullable()`) | `.min(1).nullable().optional()` | Sending `null` at creation is meaningless (absence == null). Keeps the service param `string \| undefined`. |

## Data Flow

    POST /api/pasadas  ──validateBody(PasadaIniciarSchema)──> iniciar handler
         │                                                        │
         │                                  service.iniciarPasada(lineaId, idBalanza, userId, observacion?)
         │                                                        └──> pasada.observacion ──> DB
    PUT  /api/pasadas/:id ──validateBody(PasadaUpdateSchema)──> update handler
         └─ strips action/motivoCierre ──> service.update(id, rest)

    GET  /api/lineas-produccion → toLineaDto()  (MUST list observacion explicitly)

## Interfaces / Contracts

### 1. Migration

Invocation confirmed from `mikro-orm.config.ts` + `@mikro-orm/cli@7.1.1`:

```bash
# run from the backend root; no pnpm script wraps this
npx mikro-orm migration:create
```

- v7's `cli.js` auto-discovers `./mikro-orm.config.ts` in cwd; **no `--config` flag needed**.
- TypeScript is loaded by `CLIHelper.registerTypeScriptSupport` → auto-detects `tsx` (already a devDependency). No `mikro-orm-esm` binary exists in v7.
- Output path comes from `migrations.pathTs: './src/migrations'` → `src/migrations/MigrationYYYYMMDDHHMMSS.ts`.
- **Requires a reachable database** (`DB_HOST`/`DB_PORT` default `localhost:5433`): `migration:create` diffs live schema vs. entity metadata. It also rewrites `src/migrations/.snapshot-control_pesaje.json`; commit that file with the migration.
- Fallback only if no DB is reachable: `npx mikro-orm migration:create --blank --name Observaciones` and hand-write the SQL — but the snapshot will **not** be updated, so the next real `migration:create` re-emits these columns. Prefer the non-blank path.

Expected generated body (style of `Migration20260824172250.ts`):

```ts
override up(): void | Promise<void> {
  this.addSql(`alter table "pasada" add "observacion" text null;`);
  this.addSql(`alter table "linea_produccion" add "observacion" text null;`);
}

override down(): void | Promise<void> {
  this.addSql(`alter table "pasada" drop column "observacion";`);
  this.addSql(`alter table "linea_produccion" drop column "observacion";`);
}
```

Statement order may differ by entity-discovery order; keep the generated output as emitted.

### 3. Zod schemas — `src/shared/schemas.ts`

Only **three** edits; `LineaProduccionUpdateSchema` is `LineaProduccionCreateSchema.partial()` (line 73) and inherits the field for free.

```ts
// line 65-71 — LineaProduccionCreateSchema, add:
observacion: z.string().min(1).nullable().optional(),

// line 138-141 — PasadaIniciarSchema, add:
observacion: z.string().min(1).optional(),

// line 143-146 — PasadaUpdateSchema, inside the z.object({...}) BEFORE .refine(...):
observacion: z.string().min(1).nullable().optional(),
```

`PasadaUpdateSchema` is a `ZodEffects` (`.refine` at line 147); the field must be added inside the object literal, not chained after.

### 5. `PasadaService.update()` field exception (`pasada.service.ts:175-184`)

```ts
// Fields that stay editable after the pasada is closed (completa/abortada).
const CAMPOS_EDITABLES_TRAS_CIERRE: readonly string[] = ['observacion'];

override async update(id: number, data: Partial<Pasada>): Promise<Pasada | null> {
  const pasada = await this.findById(id);
  if (!pasada) return null;

  const cerrada =
    pasada.estado === PasadaEstado.COMPLETA || pasada.estado === PasadaEstado.ABORTADA;

  if (cerrada) {
    const keys = Object.keys(data);
    const soloCamposPermitidos =
      keys.length > 0 && keys.every((k) => CAMPOS_EDITABLES_TRAS_CIERRE.includes(k));
    if (!soloCamposPermitidos) {
      throw new Error('No se puede actualizar una pasada completada o abortada');
    }
  }

  return super.update(id, data);
}
```

Behavioural properties this design guarantees:
- `{ numero: 99 }` on a closed pasada still throws the **exact same message** → `pasada.service.test.ts:151/167` and `muestra.service.test.ts:437/476` keep passing untouched.
- `keys.length > 0` keeps the throw for an empty payload `{}` (no silent no-op acceptance).
- A mixed payload `{ observacion, numero }` throws **before** `super.update`, so nothing is persisted — exactly the spec's "MUST NOT persist any field from that request, including `observacion`".
- `action`/`motivoCierre` never reach here (stripped at `pasada.controller.ts:89`), so the completar/abortar paths are untouched.

### 6. `LineaProduccionService.create()` (`linea-produccion.service.ts:66-73`)

`finalData` is an explicit allowlist, so a spread is not enough — add one line:

```ts
const finalData: RequiredEntityData<LineaProduccion> = {
  nombre: rest.nombre ?? '',
  rutaPasadaActiva: rest.rutaPasadaActiva,
  activo: rest.activo ?? true,
  observacion: rest.observacion ?? null,   // ← new
  rutaAsignadaAt: rest.rutaPasadaActiva != null ? new Date() : null,
  balanza: em.getReference(Balanza, idBalanza),
  articulo: em.getReference(Articulo, articuloId),
};
```

No signature change (`RequiredEntityData<LineaProduccion>` picks up the new optional property). `update()` (line 88-89) already forwards it via `{ ...rest }` — **no change needed there**.

## Threat Matrix

N/A — no routing, shell, subprocess, VCS/PR automation, executable-file classification, or process-integration boundary. The only external command is a developer-run `npx mikro-orm migration:create`, not runtime code.

## Migration / Rollout

Single additive migration, both columns nullable, no backfill. Rollback = run the migration's `down()` (drops both columns) and revert the branch. No data transformation, no feature flag, no phased rollout. Existing rows read back `null`, which every consumer path already renders (`?? null` in DTOs, `?? '-'` in the report).

## Open Questions

- [ ] `PasadaIniciarSchema` rejects `observacion: null` (D6). If the future UI sends `null` for an empty field instead of omitting the key, this returns HTTP 400 — coordinate with the frontend or relax to `.nullable()` later.
- [ ] `migration:create` needs a reachable database. Confirm a local Postgres is up before the apply phase, otherwise the snapshot drifts (see the `--blank` fallback caveat).
