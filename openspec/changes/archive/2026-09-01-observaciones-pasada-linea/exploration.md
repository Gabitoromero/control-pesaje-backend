# Exploration: observacion field on Pasada and LineaProduccion

## Current State

**Pasada model** (`src/models/Pasada.ts`) has no `observacion` field today. It already has `motivoCierre` (text, nullable) and `observacionCierre` (text, nullable) — both set only at close time (`completarPasada`/`abortarPasada`, via `abortarPasada`/generic `update`). These are semantically distinct from the requested "observation captured at pasada start" — must not be reused or conflated.

**`iniciarPasada` flow** (`src/services/pasada.service.ts:25-113`): signature is `iniciarPasada(lineaProduccionId: number, idBalanza: number, usuarioId: number)` — three positional scalar args, no options object. Body validated by `PasadaIniciarSchema` (`src/shared/schemas.ts:138-141`) = `{ lineaProduccionId, idBalanza }`; `usuarioId` comes from JWT (`req.user!.id`), never from body (documented as REQ-P1 in controller). Controller (`src/controllers/pasada.controller.ts:14-17,36-51`) destructures `IniciarPasadaBody` and calls the service. Adding optional `observacion` here requires: (a) extending `IniciarPasadaBody`/`PasadaIniciarSchema` with `observacion?: string`, and (b) changing `iniciarPasada`'s signature — either a 4th positional param or (cleaner, matches growing param count) refactor to an options object `{ lineaProduccionId, idBalanza, usuarioId, observacion? }`. This is a real design fork for the proposal phase.

**GET flows**: `findAllPopulated` (list) and base `findById` (detail, via `createCrudHandlers`/`getOne` in `pasada.controller.ts:72-84`) return the full MikroORM entity as JSON — no DTO/projection layer for Pasada (unlike LineaProduccion, see below). Any new entity property is automatically serialized and exposed with zero extra wiring, since there's no field allowlist.

**PUT/update flow for Pasada** (`pasada.service.ts:175-184`, `pasada.controller.ts:86-152`): generic `update` handler strips `action`/`motivoCierre` from body and forwards `rest` to `service.update(id, rest)`. `PasadaService.update` **blocks all updates once `estado` is `COMPLETA` or `ABORTADA`** (throws `'No se puede actualizar una pasada completada o abortada'`). This directly conflicts with allowing `observacion` edits after close — this is the open question flagged by the user and confirmed real: today there is no field-level exception in `update()`, it's all-or-nothing by state. Validation for the field itself: `PasadaUpdateSchema` (`schemas.ts:143-150`) currently only knows `action`, `motivoCierre`, `observacionCierre`; a bare `observacion` field would need to be added or the schema would reject/strip it depending on strictness (schema isn't `.strict()`, so unknown keys currently pass through by Zod default — worth confirming, but adding it explicitly to the schema is the correct pattern regardless, matching how `observacionCierre` was added).

**LineaProduccion model** (`src/models/LineaProduccion.ts`) has no `observacion` field. Unlike Pasada, this entity **does** have a DTO projection layer: `toLineaDto()` in `src/controllers/linea-produccion.controller.ts:32-45` explicitly lists returned fields (`id, nombre, rutaPasadaActiva, activo, estado, dispositivo, idBalanza, articuloId`). **A new `observacion` field will NOT be exposed on GET unless `toLineaDto` is explicitly updated** — this is a hard gap vs. Pasada's auto-serialization. `list`, `listInactive`, `getOne` (`linea-produccion.controller.ts:50-82`) and `assignDevice`'s response (line 128-134, separate inline shape) all use `toLineaDto` or duplicate its shape — the `assignDevice` inline DTO (lines 128-134) would also need updating for consistency, though `observacion` isn't strictly required there since it's a device-pairing endpoint (worth flagging as a proposal decision: keep or omit from that response).

**LineaProduccion PUT**: uses the **generic** `createCrudHandlers(service).update` (`routes/lineas-produccion.routes.ts:16,27`), not a custom controller method — validated by `LineaProduccionUpdateSchema` (`schemas.ts:73`, `.partial()` of `LineaProduccionCreateSchema`). `LineaProduccionService.update` (`linea-produccion.service.ts:78-143`) passes through unknown/untouched fields via `updateData: Partial<LineaProduccion> = { ...rest }` after stripping `idBalanza`/`articuloId` — so a plain scalar field like `observacion` would flow through automatically once added to the schema and entity, no extra service logic needed (no special validation like `rutaPasadaActiva`/`balanza`/`articulo` id-refs apply to a plain text field).

**Excel report** (`src/services/reporte.service.ts`): three worksheets are generated per línea — `detailSheet` (muestras), `resSheet` = **`Pasadas - ${lineName}`** (the "Pasadas" tab, lines 112-164), and `etapaSheet`. The "Pasadas" tab column order is defined at `reporte.service.ts:113-131`:
```
Línea de Producción, Balanza, Ruta, N° Pasada, Código, Artículo, Estado, Inicio, Cierre,
Duración (min), Responsable, Total Muestras, Conformes, Fuera de Rango, % Conforme,
Motivo de Cierre, Observación Cierre
```
`N° Pasada` is column 4 (key `pasadaNum`, line 117). To place the new `observacion` "right next to N° Pasada" per the request, insert a new column entry immediately after line 117 (before `Código`/`articuloCodigo`) and add the matching field in the `resSheet.addRow({...})` call (lines 145-163), e.g. `obsInicio: p.observacion ?? '-'` — following the exact existing null-coalescing pattern used for `motivo`/`obs` (`observacionCierre`) at lines 161-162. Note: there's already a column named `Observación Cierre` (key `obs`) at the end of the sheet — the new column needs a distinct header (e.g. "Observación") and a distinct key (e.g. `obsInicio` or `observacion`) to avoid collision with the existing `obs` key used for `observacionCierre`.

**LineaProduccion in reports**: `LineaProduccion` doesn't appear as a report row entity itself (reports are grouped by línea/pasada/muestra, with línea name used only as a sheet-title/grouping label, e.g. `lineName` at lines 112/166). Confirmed no `linea_produccion.observacion`-worthy column exists anywhere in `reporte.service.ts` to accidentally touch — the "must NOT export" requirement is naturally satisfied by doing nothing there.

**Migrations** (`src/migrations/`): MikroORM CLI-driven, dependency `@mikro-orm/migrations@7.1.1`, `@mikro-orm/cli` present but **no npm/pnpm script wraps it** (`package.json` scripts only has `test/build/start/seed/dev/lint/format` — no `migration:create`). Migrations are run via bare `npx mikro-orm migration:create` (or similar), presumably against `mikro-orm.config.ts` (not read this session, but implied by CLI package presence). Naming convention observed: `MigrationYYYYMMDDHHMMSS.ts` for auto-named migrations (e.g. `Migration20260824172250.ts`, `Migration20260818124240.ts`) and `MigrationYYYYMMDDHHMMSS_Name.ts` for hand/CLI-named ones (e.g. `Migration20260609000000_AuthV15.ts`, `Migration20260710000000_DevicePairing.ts`). Each migration file exports a class extending `Migration` with `up()`/`down()` using raw `this.addSql(...)` — no ORM schema-diff magic, straightforward reversible SQL. Most recent migration (`Migration20260824172250.ts`) is a clean single-column-add precedent: `alter table "dispositivo" add "unidad" varchar(10) null;` / matching `drop column` in `down()`. This is the exact pattern to follow for adding `pasada.observacion` and `linea_produccion.observacion` (two `alter table ... add "observacion" text null;` statements, either in one migration file or two — proposal should decide, but one migration touching both tables is consistent with `Migration20260710000000_DevicePairing` style multi-statement migrations). There's also `src/migrations/.snapshot-control_pesaje.json` (MikroORM's schema snapshot) which will need regeneration/update as part of `migration:create`.

**Tests**: `src/shared/schemas.test.ts` has a direct precedent — `'accepts optional observacionCierre'` test (line 343-345) parses `PasadaUpdateSchema.parse({ observacionCierre: 'nota adicional' })` and asserts the value round-trips. An equivalent test for the new `observacion` field (on both `PasadaIniciarSchema`/`PasadaUpdateSchema` and `LineaProduccionUpdateSchema`) should follow this exact shape. `pasada.service.test.ts` has an `iniciarPasada` describe block (lines 98-159) with several scenarios (missing session, wrong user, sequential numero, etc.) — no test currently touches an options/extra-field param, so a new test asserting `observacion` persists through `iniciarPasada` would be net-new, not a modification of an existing case. `reporte.controller.test.ts` references `observacion: 'ninguna'` (line 90) and `observacionCierre: ''` (line 107) as fixture data for muestras/pasadas — confirms the existing pattern for building report fixtures; a new assertion checking the new "Pasadas" tab column value would follow the same fixture style. `linea-produccion.service.test.ts` exists but wasn't read in detail this pass; given `toLineaDto`'s explicit field list, a controller-level test (not found — no `linea-produccion.controller.test.ts` file surfaced in the earlier glob) may not currently exist for the DTO shape, which is itself a coverage gap worth noting for the proposal/tasks phase.

## Approaches

1. **Extend `iniciarPasada` to an options object** — change `iniciarPasada(lineaProduccionId, idBalanza, usuarioId, observacion?)` to `iniciarPasada({ lineaProduccionId, idBalanza, usuarioId, observacion? })`.
   - Pros: scales cleanly if more optional fields get added later; self-documenting call sites; avoids positional-param confusion.
   - Cons: touches every call site (service tests currently call it positionally 6+ times) and controller call site; larger diff for a small feature.
   - Effort: Medium.

2. **Add `observacion` as a 4th trailing optional positional param** — `iniciarPasada(lineaProduccionId, idBalanza, usuarioId, observacion?)`.
   - Pros: minimal diff, existing positional call sites (tests) remain valid untouched since it's optional/appended at the end.
   - Cons: continues the positional-param pattern which doesn't scale well; slightly less readable at call sites (`iniciarPasada(1, 2, 3, 'nota')`).
   - Effort: Low.

Both approaches are compatible with the rest of the plan (model/schema/controller/report/migration changes are identical either way) — this only affects the service method signature.

## Recommendation

Approach 2 (trailing optional positional param) for `iniciarPasada`, to keep this change small and avoid unrelated churn across ~6 existing test call sites — this is a two-field additive change, not a signature redesign. Everything else (model fields, schema fields, DTO field in `toLineaDto`, report column insertion, migration) is not in question — those are mechanical and unambiguous. The one item that must be explicitly decided in `sdd-propose` (not resolved here, per the user's request) is: **should `PasadaService.update()`'s complete/abort lock exempt `observacion` edits**, or does editing an already-closed pasada's start-time observation stay blocked like every other field? Both are defensible (observación editable post-close = useful annotation; blocked = consistent immutability-after-close semantics) and this needs a product decision, not an engineering default.

## Risks

- **DTO drift**: `LineaProduccion`'s GET responses go through an explicit projection (`toLineaDto`) — if the proposal/apply phase only touches the model+schema and forgets `toLineaDto` (and the `assignDevice` inline duplicate), the field will silently not appear in GET despite being persisted and PUT-able. This is the single highest-likelihood implementation miss.
- **Report column key collision**: the "Pasadas" sheet already has a column keyed `obs` for `observacionCierre` — the new column's `key` must be distinct (e.g. `observacionInicio`) or it will silently overwrite/conflict with the existing cierre-observation column during `addRow`.
- **Naming ambiguity in code/tests**: `observacion` (new) vs `observacionCierre` (existing) vs the unrelated `Muestra.observacion` field (already exists per `MuestraRegistrarSchema`, `schemas.ts:159`, and `domain.ts:82` — a per-sample observation, a third distinct concept). Proposal/spec must be explicit about which `observacion` is being discussed in each requirement to avoid confusing implementers.
- **Open policy question**: whether `observacion` is editable on closed pasadas (see Recommendation) — must be resolved before `sdd-spec`, otherwise `update()` behavior is ambiguous and untestable.
- **Migration snapshot regeneration**: no wrapping npm/pnpm script for `mikro-orm migration:create` was found — the exact CLI invocation/config path wasn't directly verified this session (mikro-orm config file not read); worth a quick check in `sdd-propose`/`sdd-design` before assuming the invocation.
